# 排错手册（示例 · 长尾层）

> `lookup` 模式的第二个例子。命中信号：报错 / 排错 / 起不来 / 没反应 / 挂了 / 失败。

## 顺序（不许跳步）

1. **日志**：先看程序自己说了什么。找不到日志 = 先解决「日志在哪」这件事。
2. **探针**：用一条最小命令复现，而不是在完整流程里猜。
3. **源码**：前两步都指不出原因时才读代码，且要读到**具体那一行**。

跳步的代价：直接改代码 = 在不知道原因的情况下改变行为，改对了是运气，改错了多一个变量。

## 「没反应」的四种可能

| 现象 | 先查什么 |
|---|---|
| 进程没起来 | 端口占用 / 启动脚本报错 / 依赖缺 |
| 进程在但不干活 | 钩子没挂上 / 配置没生效 / 需要重启 |
| 干活了但没效果 | 改的是副本 / 缓存没清 / 看错了文件 |
| 有效果但不对 | 逻辑对，输入错 —— 回头看上游 |

## 假绿灯

**「没报错」不等于「做成了」。** 常见假绿灯：

- 脚本 exit 0，但一个字节都没改（静默跳过）
- 测试通过，但断言写的是 `true === true`
- 检查项全绿，但被检查的文件根本不存在（空检查）
- 服务起来了，但监听在错误的端口

判据永远落在**产物**上：改完的文件哈希变了没、接口返回的字段对不对、数字有没有动。

## 改完怎么验

- 一次只改一个变量
- 改完立刻用同一条命令复现，前后对比
- 保存前后两次的原始输出（不是「我记得是这样」）
