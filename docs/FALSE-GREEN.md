# FALSE-GREEN · 假绿灯清单

> 「没报错」不等于「做成了」。这份清单收集的都是**看起来通过、其实什么都没发生**的情形。
> 每一条都给出可复跑的识别方法 —— 光记住名字没有用。

## 0. 为什么单独写这一篇

检查项全绿而系统仍然坏着，是这类工具最容易出的问题。原因通常不是检查写错了，
而是**检查的对象错了**：检查了「过程有没有异常」，没检查「产物有没有变化」。

判据永远落在产物上：**哈希变了没、文件内容对不对、数字动没动。**

## 1. 静默跳过：命令 exit 0，但一个字节没改

典型：`git apply` 在非 git 目录里只打印 "Skipped patch"，退出码 0。

**识别**：改前改后各算一次哈希；一致就是没改成。
**防线**：改文件一律走「备份 → 改 → 校验 → 比 SHA」四步，比较哈希是最后一步、也是最该有的一步。

## 2. 空检查：检查项通过，因为根本没扫到东西

典型：`扫描 0 个文件，0 个有问题` → 绿。

**识别**：输出里必须带**扫描数量**，数量为 0 就是异常（而不是通过）。
**防线**：每个检查都打印 `scanned: N`；N 为 0 时按 warn 处理。

## 3. 断言写反了：`true === true`

典型：测试通过，因为断言检查的是常量。

**识别**：故意把被测对象改坏一次，看测试是否变红。没变红 = 这个测试没用。
**防线**：新加的判据必须先「见红一次」，再见绿。

## 4. 空壳包：文件在、大小为 0

典型：`package.json` 存在于是「已安装」；实际文件 0 字节（写入被中断或占位）。

**识别**：检查项除了「存在」还要有「大小 ≥ 阈值」「能 parse」。
**防线**：`checkup` 的悬空检查同时看存在与可读；空壳单独列一类。

## 5. 副本改了，活体没改

典型：两份同源文件（源目录 + 安装副本），只改了一份，运行的是另一份。

**识别**：改完比两份 SHA，不一致就是没同步。
**防线**：任何「双份文件」的改动，哈希对比是必做项，不是可选。

## 6. 改完不重启：代码是新的，进程是旧的

典型：改完立刻验证，结果全是旧行为 —— 因为进程在启动时就把模块读进内存了。

**识别**：看进程启动时间 vs 文件修改时间；进程更早 = 跑的是旧代码。
**防线**：判据里写清「这一项需要重启才生效」，验证前先确认进程启动时间。

## 7. 端口对、服务错：监听在，但不是你以为的那个

典型：端口有 LISTEN，于是「服务起来了」；实际是上一次的残留进程。

**识别**：看 owning PID 的启动时间，以及 `/status` 返回的版本号。
**防线**：状态检查同时看端口、PID、版本三者。

## 8. 观测值与判据混用：时间戳让 diff 永远不为空

典型：拆分重构后比对新旧输出，差异 300 处 —— 全是时间戳、PID、缓存计数。

**识别**：把差异一条条看完，如果全是随时间/机器变化的值，说明判据没归一化。
**防线**：差分工具里显式列一份**归一化清单**（时间戳 / 家目录 / PID / 耗时 / 计数），
清单本身写进代码注释 —— 这样「为什么这处差异不算差异」是公开的，不是事后解释。

## 9. 判据自己在名单里：检查脚本触发了自己的规则

典型：敏感词检查脚本的注释里写了敏感词，于是它永远报自己。

**识别**：跑一次，命中的全是脚本本身。
**防线**：敏感词表放**仓库外**的文件；脚本里只写「读外部名单」，不写具体词。

## 触顶判定（什么时候该停）

当「再加同义词 / 再多一条规则」带来的召回提升趋近于 0 时，就是触顶了。此时：

1. 把当前数字记进文档（几/几、阈值多少）
2. 停止加词，不启动更重的方案（向量、模型）—— 除非有明确的证据表明瓶颈不在这里
3. 写清「为什么停」——不写，下一轮的人（可能是三个月后的你）会重新尝试一遍

**宁可没有管线，也不要一条会自己长歪的管线。**
